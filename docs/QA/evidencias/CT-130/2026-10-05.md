# CT-130 — Autenticação e permissões por chave

- **Data:** 2026-10-05 (~16:07–16:20)
- **Executor:** usuário (responsável pelo projeto)
- **Commit:** sem commit (pasta sem git)
- **Ambiente:** Windows 10, Docker Desktop (contêiner `rag-postgres`, `pgvector/pgvector:pg17`), aplicação local em `http://localhost:8080`, Postman e `psql`
- **Card / requisito:** HU-009 / RF-009 (CA-03, FA-01, DP-02, RN-03) — prioridade **P1**

## Passos executados

Clientes: **Cliente A = id 6** e **Cliente B = id 7** (o roteiro usa 1 e 2; trocar os ids é permitido).

1. `GET /clients/6` sem chave.
2. `GET /clients/6` com `X-API-Key: chave-que-nao-existe`.
3. Chave do Cliente A (informada pelo usuário; não aparece no print): `POST /clients` com `{"name": "Cliente X"}`; depois, via `psql`, `SELECT count(*) FROM client WHERE name = 'Cliente X';`.
4. Chave do administrador (não aparece no print): `POST /clients/1/search` com `{"question": "franquia"}`.
5. Chave do Cliente A (não aparece nos prints): `GET /clients/7` (existe) e `GET /clients/999` (não existe).
6. Chave do Cliente A: `GET /clients/6`.

## Resultado esperado

1 e 2: `401`, `title` `Não autenticado`. 3 e 4: `403`, `title` `Acesso negado`. 5: as duas respostas `403` com corpo idêntico, exceto `instance` (não dá para saber se o 999 existe). 6: `200`. Nenhum cliente "Cliente X" no banco.

## Resultado obtido

```text
1. sem chave                      →  401 "Não autenticado" (detail cita o cabeçalho X-API-Key)
2. chave-que-nao-existe           →  401 "Não autenticado" (mesma resposta)
3. Cliente A: POST /clients       →  403 "Acesso negado", instance /clients
   psql: count(*) client WHERE name = 'Cliente X'  →  0
4. admin: POST /clients/1/search  →  403 "Acesso negado", instance /clients/1/search
5. Cliente A: GET /clients/7      →  403 "Acesso negado", instance /clients/7
   Cliente A: GET /clients/999    →  403 "Acesso negado", instance /clients/999
     corpo /clients/7:   {"detail":"Você não tem permissão para acessar este recurso.","instance":"/clients/7","status":403,"title":"Acesso negado","type":"about:blank"}   (496 B)
     corpo /clients/999: {"detail":"Você não tem permissão para acessar este recurso.","instance":"/clients/999","status":403,"title":"Acesso negado","type":"about:blank"} (498 B)
     → idênticos exceto instance; os 2 bytes a mais são o "99" do instance
6. Cliente A: GET /clients/6      →  200 {"id": 6, "name": "Cliente A", ...}
```

## Observações

- Uma primeira versão desta evidência, no mesmo dia, registrou a execução sem o `/clients/999` (parcial). Esse passo foi executado e entregue depois, ainda em 2026-10-05: a resposta para o cliente que não existe é igual à do cliente que existe, exceto `instance`, então não dá para saber se o 999 existe.
- Esse ponto também é conferido pelo automático CT-081 (`SecurityConfigTest`, "403 não revela se o outro cliente existe") e pela linha `/clients/999/search` da `security-matrix.csv` (CT-080), ambos OK. O roteiro manual pede a confirmação com a aplicação real.
- Nos passos 3 e 4 a chave usada não aparece no print; o usuário informou qual foi.
- No passo 4 o administrador buscou em `/clients/1` em vez do id do Cliente A; a regra conferida é a mesma (o administrador não busca nos documentos de um cliente).
