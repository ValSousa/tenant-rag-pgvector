# CT-119 — Administrador cadastra Cliente A e Cliente B pelo Swagger UI

- **Data:** 2026-10-05
- **Executor:** usuário (responsável pelo projeto)
- **Commit:** sem commit (pasta sem git)
- **Ambiente:** Windows 10, Docker Desktop (contêiner `rag-postgres`, `pgvector/pgvector:pg17`), aplicação local em `http://localhost:8080`, Swagger UI e `psql`
- **Card / requisito:** HU-003 / RF-003 (CA-01); RF-009 DP-01 — prioridade P2

## Passos executados

1. Swagger UI → **Authorize** com o esquema `apiKey` (cabeçalho `X-API-Key`), informando a chave do administrador → **Authorized**.
2. `POST /clients` (descrição: "Somente administrador. A apiKey é mostrada só nesta resposta.") com `{"name": "Clinete - A"}`.
3. `POST /clients` com `{"name": "Cliente -B"}`.
4. Chaves guardadas pelo usuário (cobertas nos prints).
5. `SELECT id, name, api_key_hash, created_at FROM client ORDER BY id;` — conferido via `psql` em 2026-10-05 (sem print).
6. Complementar: `POST /clients` com `{"name": "Select * from client"}`.

## Resultado esperado

- As duas chamadas respondem `201`, com cabeçalho `location: /clients/{id}` e corpo com `id`, `name` e `apiKey` não vazia; as duas chaves são diferentes.
- No banco, `api_key_hash` tem 64 caracteres hexadecimais e é diferente da `apiKey` devolvida (só o hash é guardado).

## Resultado obtido

```text
1. Authorize: apiKey (apiKey), header X-API-Key → Authorized (valor mascarado)

2. POST /clients {"name": "Clinete - A"}   → 201  {"id": 3, "name": "Clinete - A", "apiKey": "<coberta>"}
3. POST /clients {"name": "Cliente -B"}    → 201  {"id": 4, "name": "Cliente -B",  "apiKey": "<coberta>"}
   As duas apiKey são diferentes.

5. psql: 5 clientes na tabela client; todos com api_key_hash de 64 caracteres
   hexadecimais (api_key_hash ~ '^[0-9a-f]{64}$' verdadeiro para todos).

6. POST /clients {"name": "Select * from client"} → 201  {"id": 5, "name": "Select * from client", "apiKey": "<coberta>"}
```

## Observações

- O banco não estava zerado: os clientes novos receberam os ids 3 e 4 em vez de 1 e 2. O roteiro permite trocar os ids pelos devolvidos no cadastro (Preparação, item 2).
- O nome "Clinete - A" tem erro de digitação; não afeta o teste.
- O cabeçalho `location` não aparece: o print corta antes de **Response headers**. Ele é conferido pelo teste automático CT-020 (`ClientControllerTest`, OK), então fica como observação, sem impedir o veredito.
- O passo 5 não tem print: foi conferido via `psql` em 2026-10-05. A comparação hash x `apiKey` é garantida pelo formato (64 hexadecimais, SHA-256), diferente do formato da chave devolvida.
- **Nome "Select * from client" (anexo `2026-10-05-nome-sql.png`):** o valor foi gravado como texto literal. A gravação usa JPA com consultas parametrizadas, então nada foi executado e a tabela `client` ficou intacta (o cliente 2, "select * from tabela", de 2026-10-02, é o mesmo caso). O RF-003 hoje só exige nome obrigatório e com até 255 caracteres (RN-01), então isso não viola o requisito atual e não é bug do HU-003. O usuário considera aceitar esse tipo de nome uma vulnerabilidade de segurança e decidiu tratar a restrição de formato do nome em um card separado, a ser criado pelo planejador.
