## Observações

- Os testes de isolamento (`TenantIsolationIT`) vão de ponta a ponta: `POST /clients/{id}/search` com a chave do cliente → `SearchService` → `ChunkRepository.searchByClient` → `PgVectorEmbeddingStore` → PostgreSQL + pgvector do Testcontainers. O dono de cada resultado é conferido no banco (`SELECT client_id FROM document_chunk WHERE embedding_id = ?`), não só pelo texto. Os vetores são fixos (`FakeEmbeddingModel.fixo`), com o chunk do outro cliente idêntico à pergunta.
- `SET LOCAL hnsw.iterative_scan = strict_order` roda na mesma transação da busca (`@Transactional(readOnly = true)` no `ChunkRepository`), antes do `embeddingStore.search`; a imagem `pgvector/pgvector:pg17` aceita o parâmetro (pgvector 0.8+). Com o volume dos testes o PostgreSQL usa varredura sequencial, então o efeito do ajuste não é medido aqui (arquitetura 04, seção 5.3).
- SQL gerado pelo `PgVectorEmbeddingStore` 1.20.2-beta30 com o filtro (lido no código-fonte da biblioteca): `... WHERE <minScore> AND client_id::bigint is not null and client_id::bigint = <clientId> ORDER BY embedding <=> '<vetor>' LIMIT <topK>` — o filtro por cliente fica no SQL (RF-007 RN-01, CA-05).
- O `topK` é validado no `SearchRequestDTO` (1 a 20; texto não numérico → 400 pelo JSON ilegível); o padrão 5 é aplicado no `SearchService`, que também limita ao máximo (`app.rag.default-top-k`, `app.rag.max-top-k`). Por isso, no CT-061, o web slice confere que o controller repassa o valor recebido (nulo quando ausente) e o `SearchServiceTest` confere que o repository recebe 5.
- O passo 2 do fluxo principal do RF-007 ("confirma que o cliente existe") é garantido pelo controle de acesso: só a chave do próprio cliente passa por `/clients/{clientId}/**`, e o cliente da chave existe; não há consulta extra.
