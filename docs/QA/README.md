## Como usar no desenvolvimento

1. Abra o requisito em `docs/requirements/` e vá até a seção **"Cenários de teste (QA)"**.
2. Para cada `CT-xxx` listado, leia o cenário em [05](05%20Cenarios%20de%20teste.md): ele diz o nível, a classe de teste e o que verificar.
3. Escreva o teste com o ID no `@DisplayName` (`"CT-110 — ..."`) — de preferência antes do código de produção.
4. Se o cenário usa massa de dados, ela está em [04](04%20Testes%20orientados%20a%20dados.md) e vai para `src/test/resources/ddt/`.
5. Rode `./mvnw test`. A etapa do plano só termina quando os cenários listados em [01, seção 7](01%20Estrategia%20de%20testes.md) passam.
6. Atualize o status do cenário no dashboard (`Testes/Testes.json`, lista `cenarios`) e registre a evidência ([01, seção 11](01%20Estrategia%20de%20testes.md)). Status: Não iniciada → OK → Concluído; Bug quando falha; Bloqueado quando depende de decisão.

Tipo de execução de cada cenário: **JUnit** (automatizado, `mvnw test`) ou **Manual** (executado por uma pessoa: roteiro do [07](07%20Testes%20manuais.md) ou teste opt-in com OpenAI real, disparado à mão com `-Dgroups=openai`). Hoje: 80 JUnit e 28 Manual (25 roteiros de nível M e 3 opt-in de nível O: CT-035, CT-075, CT-076).

## Regras que não mudam

- `mvnw test` não chama a OpenAI e não precisa de `OPENAI_API_KEY`; precisa só do Docker.
- Cenários **P1** (isolamento entre clientes, segurança, gravação parcial) não podem falhar nem ser desabilitados.
- Isolamento entre clientes é testado contra PostgreSQL + pgvector real; mock não conta.
- Todo endpoint novo entra na matriz `security-matrix.csv`.
